## Latency design

ScreenCaptureKit audio-only callbacks convert PCM directly into a bounded SPSC ring. There is no video encoder, recording file, cloud relay, Mac relay or extra callback staging queue. Requested capture rate is a supported native 48 kHz; conversion to the receiver's 44.1 kHz occurs once in the sender. Extra reserve uses actual source-rate frames. Lowest latency requests 2 ms extra reserve, 352-frame packets and independent 45 ms receiver/presentation targets. At the user's request, Stable now uses a 100 ms reserve and 1000 ms receiver/presentation targets, and is the initial default. Manual retains 44/88/352-frame packets. Compression is optional and disabled initially. Existing nonmanual presets migrate to the current values; manual values are preserved.

The 45 ms minimum comes from this user's Android/HomePod observations, not an iOS acoustic measurement. The operating system chooses capture callback period. The network loop waits for its next absolute sender deadline or socket activity, with a 20 ms ceiling during otherwise idle work; it does not add a fixed 20 ms wait to packets. Removing the earlier 1 ms idle cap avoids unnecessary wakeups between packet deadlines. Neither short packets nor a short poll establish a matching capture or transmission latency. Source callbacks can already contain older samples; splitting a delivered block does not make them arrive earlier.

Optional Darwin `SO_NET_SERVICE_TYPE/NET_SERVICE_TYPE_AV` applies only to this sender's UDP sockets and is read back for diagnostics. It does not request the VoIP class, change router settings or alter global traffic policy. Native TCP RTT has millisecond granularity; rounded-zero samples remain unavailable, rather than implying zero delay. TCP RTT is not UDP one-way latency.

Diagnostics separate delivery age, capture block span/interval, callback work, queue depth, actual packet span, encoding maximum, socket-call time, TCP RTT, receiver bounds, deadline lead, refusal/fallback and stream counters. Peak/nonzero input counters distinguish silence from real input without saving PCM. Last measurements survive a disconnect; the exported diagnostic current-state fields identify whether a connection/capture is still active.

Each connection starts muted and requires the initial mute acknowledgement before audio. Application volume supports 0–100%; assistant listening tests are limited to 20%.

The app explicitly activates a playback audio session with `mixWithOthers`, without ducking or interrupting the source application. The audio background mode accompanies screen capture for ongoing network streaming. The standard system-volume control is separate from the receiver slider and never forwards volume changes into the native receiver-volume setter. This configuration still needs a physical volume-change regression check. Public `setOutputMuted` affects only this app's own session; it cannot mute another app locally while preserving captured audio. No automatic global mute is claimed or applied.

Live telemetry is observed only by the diagnostic view. Stable connection/status values are no longer republished every 250 ms, and optional numeric JSON export writes on a utility queue. A simulator-only metric generator exercises diagnostic scrolling without networking or recording. The UI regression reaches the last diagnostic row and verifies that continued updates do not reset the scroll position.

The iOS sender opts into bounded recovery after its presentation deadline is missed: advance monotonic RTP time to the current packet boundary, discard expired input, and issue a synchronization packet. The default behavior of the shared transport remains unchanged for other clients. The 48 kHz resampling path now honors the input reserve and reports actual underruns. UDP sends explicitly request nonblocking behavior where supported. Native tests cover resampler reserve, starvation and recovery after a simulated one-second stall; receiver handling of this recovery requires physical verification.

## Remaining physical verification

The user established sharing and reported audible but heavily interrupted playback in the lowest-latency mode. Device counters confirmed successful receiver negotiation, nonzero captured audio and 20 ms source blocks. Sender measurements also showed prolonged scheduling stalls, frame drops and a pacing deadline more than ten seconds behind in one session. These are observed symptoms, not proof that the network or codec alone caused them. Small wire packets cannot shorten a capture block that has already arrived, so the revised presets use 352-frame packets to reduce packet count fourfold relative to 88 frames while retaining the low receiver target.

The user also reported that adjusting system volume silenced the receiver and that Diagnostics could not scroll during sharing. The fixes above passed native and simulator checks; physical listening, background continuity, system-volume changes and acoustic end-to-end latency must be checked on the updated build. No measured acoustic improvement, universal app compatibility or resolved stutter is claimed from these automated tests.

After the mixable-session/scroll/recovery update, actual device diagnostics confirmed `mixWithOthers` and an active playback session. Nonzero captured input continued at system volume zero. The user still reported intermittent playback, with a rough/rasping sound in Lowest latency; Stable removed that roughness but still interrupted. No receiver setup rejection, local send error or resend request was recorded in the sampled sessions. The low target is therefore not established as usable on this iOS path.

The next diagnostic build records the maximum sender-cycle elapsed time and the thread CPU time from that same cycle, excluding the connection handshake, plus coarse power/thermal/app-state context and snapshot time. Elapsed socket/encode maxima include descheduling and must not be presented as pure kernel or codec CPU cost. Fixed 352-frame uncompressed ALAC now uses byte packing instead of per-bit loops, with the same wire format. A two-second, two-channel sine regression checks 48-to-44.1 kHz conversion across 20 ms source blocks and packet boundaries in both plaintext and authenticated/encrypted modes; Apple's decoder checks the encrypted ALAC output against the expected waveform.

An Apple Silicon Mac `clang++ -O3` microbenchmark over 50,000 352-frame packets measured approximately 4.56 µs/packet before byte packing and 0.37 µs afterward. This is a local codec CPU comparison, not an iPhone or acoustic latency measurement. The sender's diagnostic queue now includes unconsumed resampler staging as well as the ring. Ring capacity and the producer watermark accommodate the entire 0–100 ms manual reserve range; the old fixed 40 ms watermark could prevent larger reserves from ever priming. Capacity does not impose a fixed queue delay.

The user reported improvement but continued interruption after this update. A background device snapshot showed a longest sender loop of about 2029.67 ms with only 0.622 ms of thread CPU time, and no local send errors. This demonstrates waiting/descheduling rather than two seconds of codec CPU, but does not distinguish kernel socket waiting from scheduling policy. Foreground listening comparison was unavailable; an attempted Instruments attachment could not resolve the running process, so no successful trace is claimed.

The next beta requests a public `AudioWorkIntervalCreate` workgroup plus a preemptible `THREAD_TIME_CONSTRAINT_POLICY` on the dedicated sender thread, only after authentication and real capture input. Computation budget is capped at 0.5 ms or one quarter of the packet period, whichever is smaller. It falls back instead of repeatedly promoting a demoted thread. `scheduling_test` checks interval operation and return to standard policy on an isolated Mac thread without audio/network output. Darwin's Mach policy opts this thread out of pthread QoS; restoring standard policy does not restore pthread QoS membership. The dedicated thread exits after cleanup. iOS application success and audible improvement remain unverified until sharing is restarted.

iPhone Duo outer-display UI was checked at 1398×2034. The inner display and hinge transition remain unverified; standard adaptive SwiftUI layout is implemented, but no physical Duo is connected. Device Hub owns the hinge posture: powering off a simulated display is not an equivalent fold test. Mac desktop-operation tooling was not installed, so no Device Hub pose interaction was performed.
